## 2. Forensic Audit Findings & Root-Cause Analysis

### Finding 1: Contradictory Backend Status & Loopback Warning on Public Hosted Dashboard
- **Observed Defect**: When the public dashboard at `https://cyberdrivepro.github.io/cybervps-space-station/` is loaded, it shows a warning "Loopback Target Configured on Hosted Web Dashboard" and displays "Control Plane Backend Offline", despite Railway control plane (`https://cybervps-space-station.up.railway.app/health`) being healthy.
- **Root Cause Analysis**:
  1. **Inline CSS Syntax Collision**: In root `index.html` (line 979), the element `<div id="loopback-warning-banner" ... style="display:none; ... display:flex; ...">` contained both `display:none` and `display:flex` within the same inline style attribute. The browser CSS parser applies the last declaration (`display:flex`), causing the warning banner to render immediately before any JavaScript probe evaluates.
  2. **Dual Conflicting Storage Keys**: `apps/dashboard/src/core/state.js` read and wrote to `cvps_control_plane_url`, while `index.html` read and wrote to `cvps_server_url`. If a workstation developer previously stored `http://localhost:8080` under `cvps_control_plane_url`, loading GitHub Pages would read the stored localhost target and fail due to browser Mixed-Content security (HTTPS page attempting HTTP connection to localhost).
  3. **Lack of Synchronized Endpoint Resolution**: Neither script checked whether a stored localhost value was overriding the default production Railway endpoint on a hosted domain.
- **Remediation Specification**:
  - Unify the endpoint resolution priority:
    1. Explicit validated `?backend=` query parameter.
    2. Explicit user-configured saved URL.
    3. If running on a public remote host (e.g. `github.io`, `netlify.app`) and the saved target is loopback, automatically recover to `https://cybervps-space-station.up.railway.app` unless an explicit query parameter was passed.
    4. Origin if self-hosted with HTTP/HTTPS.
  - Fix inline style attribute on `#loopback-warning-banner` so it defaults strictly to `display:none`.
  - Keep initial connection status as `UNKNOWN` / `VERIFYING` until the async `/health` probe resolves.

### Finding 2: Unverified Statuses, Premature Health Claims & Inferred Telemetry
- **Observed Defect**: The UI displayed "Connected Control Plane ... HEALTHY", "QUORUM HEALTHY", `epoch_1_tok_1`, "SFTP: Ready (Port 22)", and "NLA: Active" even when no backend check had run or when no host agent was connected.
- **Root Cause Analysis**:
  1. In `apps/dashboard/src/core/state.js` (line 16), `systemHealth` was hardcoded to `{ score: 100, status: 'HEALTHY' }`.
  2. In `services/cluster/cluster-state.js` (lines 433-450), `initializeDefaultMesh()` populated 5 default cluster nodes with `observed_state: 'healthy'` and synthetic `latency_ms: 1` before sending a single network packet.
  3. In `index.html`, protocol status strings like "SFTP: Ready" and "NLA: Active" were statically hardcoded into table rows rather than bound to real capability inspection objects.
- **Remediation Specification**:
  - Replace initial health score with `{ score: null, status: 'PENDING_VERIFICATION' }`.
  - Default all cluster nodes to `observed_state: 'unverified'` and `latency_ms: null` until verified by `RecoveryCoordinator` / independent health checks.
  - Implement a 5-state lifecycle model (`NOT_CONFIGURED` $\rightarrow$ `DISCOVERED` $\rightarrow$ `REACHABLE` $\rightarrow$ `AUTHENTICATED` $\rightarrow$ `VERIFIED`).
  - Derive protocol capabilities (SFTP, NLA, RDP) dynamically from host agent telemetry.

### Finding 3: Hardcoded Credential-like Values & Insecure Fallbacks
- **Observed Defect**: Source code contained default credentials:
  - `api/middleware/auth-guard.js`: Default fallback admin password `'cybervps_admin_2026'`, pairing key `'cybervps_pair_station_2026'`, and enrollment token `'cvps_enroll_master_token'`.
  - `services/server.js`: Default admin password fallback `'Cyberexpert2026!'`.
  - `apps/dashboard/src/core/state.js` and `index.html`: Automatically populated `'cybervps_pair_station_2026'` into `localStorage` if empty.
- **Root Cause Analysis**: Development convenience defaults were left active in production code paths without environment checks.
- **Remediation Specification**:
  - Enforce fail-closed security in production (`NODE_ENV === 'production'`): if required secrets are absent, reject requests or generate an ephemeral cryptographically strong secret with an audit warning.
  - Do not automatically inject public default pairing keys into browser `localStorage`.
  - Enforce strict server-side role separation: `administrator`, `operator`, `agent`, and `public`.

### Finding 4: Inconsistent Build Metadata & Commit SHAs
- **Observed Defect**: Different commit identifiers were found across the codebase (`302aa7d` in `/health`, `cc24d44` in `/api/v1/health`, while git HEAD was `57bf173`).
- **Root Cause Analysis**: Static string literals were hardcoded in different route handlers in `services/server.js`.
- **Remediation Specification**:
  - Implement a single, dynamic build metadata resolver in `services/server.js` that checks `process.env.RAILWAY_GIT_COMMIT_SHA || process.env.GIT_COMMIT_SHA` or dynamically queries `git rev-parse --short HEAD` (with fallback to package version).
  - Synchronize both `/health` and `/api/v1/health` to return identical build metadata.

### Finding 5: Remote Desktop (RDP / VNC / RustDesk) Reality & Multi-Layer Modeling
- **Observed Defect**: The dashboard presented RDP connection buttons and displayed localhost port mappings (e.g. `127.0.0.1:33890`) without independent verification of whether a local bridge daemon was running or whether the remote Windows host had TermService enabled.
- **Root Cause Analysis**:
  - `127.0.0.1:33890` is a client-side local listener on the operator's PC, not an address on the remote VPS or on Railway.
  - Without a local client bridge running, pointing an RDP client to `127.0.0.1:33890` fails with connection refused.
- **Remediation Specification**:
  - Model RDP readiness across 5 distinct, independently verified layers:
    1. **Target Enrollment & Heartbeat**: Machine is enrolled and reported recent heartbeat.
    2. **Host Remote Desktop Service**: TermService is verified running on target Windows host.
    3. **Agent Outbound Relay**: Target host agent has active WebSocket relay session.
    4. **Local Bridge Listener**: Operator PC bridge daemon is active and listening on client loopback.
    5. **Protocol Handshake & NLA**: RDP negotiation completes with valid credentials.
  - If no dedicated Windows test VM is connected, report automated test status truthfully as `BLOCKED (Requires Dedicated Windows VM)` rather than claiming PASSED.

### Finding 6: Navigation Architecture & Modular View Coverage
- **Observed Defect**: The existing dashboard navigation laid out 19 modules as an unstructured vertical list without clear domain grouping, making navigation on mobile/tablet difficult and causing visual clutter.
- **Remediation Specification**:
  - Group all 19 modules into 7 enterprise-grade navigation domains:
    1. **Mission Control** (Overview, Global Search, Notifications)
    2. **Fleet & Inventory** (Instances Fleet, Device Intel, Applications, Processes & Services, Infrastructure Registry, Path Ownership Explorer)
    3. **Connectivity** (TCP Port Bridge, Virtual Mesh, All-Port Explorer, Public Tunnels, WireGuard & Infra, Connection Graph)
    4. **Remote Access** (Remote Desktop, Web Terminal, File Manager / SFTP, Interactive App Sessions)
    5. **Resilience** (Multi-Backend HA / End-Core, Disaster Recovery, Replication & Backups, Path Conflicts, Recovery History)
    6. **Platform Services** (Custom Hosting, Domains & Deployments, Docker & Sandboxes, Plugins)
    7. **Operations & Administration** (System Doctor, Activity Logs, Security & Permissions, Settings, Build Metadata)
